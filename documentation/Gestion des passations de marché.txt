# 6. OBJECTIF DU MODULE

Créer ou faire évoluer le module **Gestion des passations de marchés**.

Le module est destiné principalement aux **agents de la cellule de passation des marchés**.

Il doit permettre de :

* Créer et gérer les marchés ;
* Planifier automatiquement les différentes phases ;
* Suivre leur réalisation ;
* Documenter chaque phase ;
* Détecter les retards ;
* Envoyer des alertes ;
* Gérer les entreprises et consultants ;
* Gérer les offres techniques et financières ;
* Gérer l'attribution ;
* Produire la situation d'un marché ;
* Produire des statistiques ;
* Fournir à la Direction Générale une vision globale des passations.

---

# 7. TYPES DE MARCHÉS

Le système doit gérer plusieurs **types de marchés**.

Chaque type de marché possède un ensemble de **phases prédéfinies**.

Pour chaque phase, prévoir notamment :

* Nom ;
* Description ;
* Ordre ;
* Durée prévue ;
* Unité de durée ;
* Phase obligatoire ou optionnelle ;
* Statut actif/inactif.

## Paramétrage

Les types de marchés et leurs phases doivent être **entièrement paramétrables depuis l'administration système**.

L'administrateur doit pouvoir :

* Créer un type de marché ;
* Modifier un type ;
* Activer/désactiver un type ;
* Ajouter une phase ;
* Modifier une phase ;
* Supprimer ou désactiver une phase ;
* Définir l'ordre des phases ;
* Définir leur durée ;
* Définir si elles sont obligatoires ou optionnelles.

---

# 8. CRÉATION D'UN MARCHÉ

Lors de la création d'un marché, l'utilisateur doit sélectionner un **type de marché**.

Le système doit automatiquement récupérer les phases associées à ce type.

Prévoir notamment :

* Référence du marché ;
* Objet/intitulé ;
* Type de marché ;
* Date de début prévisionnelle ;
* Date de fin prévisionnelle ;
* Responsable/agent chargé du marché ;
* Description ;
* Montant estimatif, si applicable ;
* Observations.

---

# 9. DOCUMENTS DU MARCHÉ

À la création d'un marché, permettre de joindre les documents nécessaires.

Par exemple :

* TDR ;
* Dossier d'appel d'offres ;
* Cahier des charges ;
* Documents administratifs ;
* Autres documents nécessaires à la procédure.

Utiliser autant que possible le système GED/documentaire déjà présent dans l'application.

---

# 10. PLANIFICATION AUTOMATIQUE DES PHASES

Lorsqu'un type de marché est sélectionné et que la **date de début prévisionnelle** est renseignée, le système doit automatiquement planifier toutes les phases.

Pour chaque phase, calculer :

* Date de début prévisionnelle ;
* Date de fin prévisionnelle ;
* Durée ;
* Ordre.

Exemple :

Début du marché : 01/09/2026

* Phase 1 : 5 jours ;
* Phase 2 : 10 jours ;
* Phase 3 : 7 jours ;
* Phase 4 : 3 jours.

Le système calcule automatiquement les dates de chaque phase.

Si la date de début prévisionnelle du marché est modifiée, la planification doit être recalculée selon les règles définies.

Prévoir une représentation visuelle de la planification, idéalement sous forme de :

* Timeline ;
* Ou diagramme de Gantt simplifié.

---

# 11. RÉALISATION DES PHASES

Chaque phase doit être suivie individuellement.

Afficher notamment :

* Phase ;
* Durée prévue ;
* Début prévisionnel ;
* Fin prévisionnelle ;
* Début réel ;
* Fin réelle ;
* Statut ;
* Justificatif ;
* Observations.

Conserver séparément les données :

### Planification

* Début prévisionnel ;
* Fin prévisionnelle.

### Réalisation

* Début réel ;
* Fin réelle.

Les dates réelles peuvent être différentes des dates prévisionnelles.

Le système doit permettre de mesurer les écarts.

---

# 12. JUSTIFICATIF OBLIGATOIRE

Pour valider la réalisation d'une phase, un **document justificatif est obligatoire**.

Lorsque l'utilisateur clique sur **« Valider la réalisation »** :

1. Vérifier si un justificatif existe.
2. Si aucun justificatif n'existe, empêcher la validation.
3. Proposer immédiatement à l'utilisateur de joindre le justificatif.
4. Après ajout du document, permettre la validation.
5. Enregistrer automatiquement la date de réalisation réelle.

Conserver les documents associés à chaque phase.

---

# 13. GESTION DES RETARDS

Comparer automatiquement :

**Date de fin prévisionnelle**

avec :

**Date de fin réelle**

ou, si la phase n'est pas terminée :

**Date du jour**.

Si la date prévisionnelle est dépassée et que la phase n'est pas terminée, la phase doit être considérée comme **en retard**.

Prévoir des statuts clairement identifiables :

* À venir ;
* En cours ;
* Réalisée ;
* Réalisée dans les délais ;
* Réalisée en avance ;
* Réalisée en retard ;
* En retard.

---

# 14. ALERTES PAR E-MAIL

Le système doit envoyer automatiquement des alertes par e-mail concernant les phases.

Prévoir notamment :

* Rappel avant échéance ;
* Notification à l'échéance ;
* Notification de retard ;
* Rappels périodiques pour les phases toujours en retard.

Les destinataires doivent être définis selon les règles de gestion et les rôles utilisateurs.

Lorsque le système possède déjà un mécanisme de notification, le réutiliser.

Prévoir si possible le paramétrage :

* Activation/désactivation ;
* Fréquence ;
* Destinataires ;
* Modèles d'e-mails.

---

Les offres techniques et financières doivent pouvoir être jointes sous forme de documents.
